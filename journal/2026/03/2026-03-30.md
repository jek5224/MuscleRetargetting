# Research Journal — 2026-03-30

## Fix: Separate Contours After Cut

### Problem
After cutting contours into streams via the Optimize path, the two pieces at each CUT level had no shared boundary vertices. The cutting line was missing — each piece was just an open arc of the original contour with no connection to the other piece.

### Root Cause
`_cut_contour_bp_transform` has two piece-building paths:
1. **Crossing-based** (when shared edges between optimized sources cross the target contour) — creates proper intersection vertices
2. **Vertex assignment fallback** (when crossings aren't found) — just splits vertices into groups by nearest centroid, NO shared boundary vertices

The Optimize button calls `_optimize_remaining_pieces` → `_cut_contour_bp_transform`. For many muscles, the crossing detection fails (optimized source polygons don't have close enough vertices to form shared edges), so the fallback is used. The fallback produced pieces without the 2 intersection vertices where the cutting line meets the contour.

### Fix
In the vertex assignment fallback, use the cutting line from optimization (`_shared_cut_edges_2d`) to intersect with the target contour edges. This creates exactly 2 new vertices at the crossing points, then splits the contour at those points so both pieces share the intersection vertices. Falls back to perpendicular bisector of piece centroids if no shared edge is available.

### Debugging Lesson

Wasted hours because I didn't trace the actual code path:

1. **Assumed wrong code path.** Assumed pieces came from `_apply_iterative_cut` (manual line cut). Never checked that the Optimize button calls a different path: `_optimize_remaining_pieces` → `_cut_contour_bp_transform` → vertex assignment fallback.

2. **Didn't read the UI code.** `zygote_mesh_ui.py` shows exactly which function each button calls. Should have read that first — the Optimize button at line ~4985 calls `_optimize_remaining_pieces`, not `_apply_iterative_cut`.

3. **Added workarounds instead of finding the source.** Spent hours adding post-processing (snap vertices, reconstruct contour, re-split) — all wrong because the fix needed to be in the function that PRODUCES the pieces, not after they're stored.

4. **Didn't add the right diagnostic early.** Should have immediately printed which function produces the pieces, not just checked the output after storage.

**Rule: When output is wrong, trace from UI action → function call → data production. Read the UI event handlers. Fix at the source, never post-process.**

## pyuipc Bake: L+R UpLeg Walk (No Contact)

Successfully baked 50 muscles (25 L + 25 R UpLeg) for walk1_subject1.bvh frames 0-131 using pyuipc IPC solver on A6000 server.

### Results
- **~77 seconds total** (0.58s/frame), 1-2 Newton iterations per frame
- 84,762 DOFs, 54,672 tets across all muscles
- ~5-6% tet inversions (worst: Pectineus 22%, Gluteus Maximus 20%)
- Contact disabled — SPC+IPC didn't converge (SPC pulls muscles into overlap, IPC pushes apart → oscillation)

### Pipeline
1. `bake_pyuipc.py` — skeleton-driven LBS with SPC constraints, pyuipc elastic solve
2. `convert_pyuipc_to_cache.py` — un-remaps vertices, converts mm→viewer scale, writes chunk npz files
3. Viewer loads cache via `_motion_load_cache` when playing walk1_subject1.bvh
